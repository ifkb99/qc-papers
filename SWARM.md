# QSim swarm protocol

This is the shared protocol for future QSim swarm assignments on Codex and
Claude Code. CLAUDE.md owns repository conventions and validation; METHOD.md
owns scientific method. Claims, notes and TODOs retain their existing homes.
SWARM_REVIEW_2026-09-12.md records the review and adoption decisions.

These rules do not restart, reassign or retroactively relint live/frozen work.
Apply them when opening the next task or scientific revision. User intent and
existing authorization govern scope; loading this file grants no permission
to delegate, execute science, publish or commit. A side conversation remains
an observer unless the user explicitly authorizes its particular mutations.
Do not take over the main coordinator or contact its agents from a side chat.

## Entrypoints and ownership

- Codex loads `~/.codex/skills/qsim-research`; the Luna coordinator adapter
  applies only when Luna is coordinating or the user requests that division.
- Claude loads `~/.claude/skills/qsim-research`, with `qsim-swarm` and
  `qsim-worker` supplying host mechanics. Both hosts read this file instead
  of maintaining separate copies of the protocol.
- One coordinating session owns the `coordinator` actor and canonical writes.
  Parallel workers use distinct actor IDs and write only in their assigned
  attempt output directories. Reviewer notes/mutants go in an assigned review
  directory `out/agent-board/reviews/NAME/`, never into submitted evidence. Actor identity is cooperative,
  not an authentication or filesystem boundary.
- The board owns live state: open assignments, their owners and their lease
  freshness. Do not restate a round's state in `HANDOFF.md`, whose state block is
  generated by `tools/handoff.py` from the board, git and `todo/open`; the
  coordinator regenerates it when a round opens or closes and leaves the
  hand-written part for the current direction and the caveats that change how a
  headline reads. An expired lease on an open assignment means the work stopped
  or was abandoned, not that it is running; confirm the process before reclaim.
- Pass `arb --project /absolute/research/root --actor ACTOR ...` explicitly.
  Use only an actor assigned to this session. Observers use read operations,
  not another session's resume/inbox/ack. Resume and inbox create delivery
  receipts; only ack advances that actor's consumed cursor.
- Do not put current QSim workers in ordinary git worktrees: this dirty
  workspace contains untracked claims/config and ignored board artifacts.
  `not_initialized` means check the supplied root; do not create a second board.
- **Sealed inputs.** A claim seals each input file's hash. Editing one makes the
  attempt stale, which blocks its submission, review and closure.
  - Before editing a canonical file, the coordinator runs
    `uv run python tools/swarm.py inflight PATH`. On Claude, the project hook
    in `.claude/settings.json` asks first for Edit/Write/MultiEdit/NotebookEdit.
    That check does not see shell writes such as `sed -i`. A second hook,
    `tools/swarm.py seals --hook`, runs after Bash and every edit tool. It
    compares each sealed input with its recorded hash, so it catches a
    broken seal however the file was changed, and reports each break once.
    `uv run python tools/swarm.py seals` lists the current breaks.
  - Prefer inputs that stay fixed during a round. Snapshot contract text into
    `out/` rather than listing a row the coordinator expects to integrate into.
  - If the attempt's work stays valid after an edit, the coordinator records
    that with `arb call task.accept_input_change task=T input=PATH reason=...`.
    The call re-seals that one input in place and keeps the attempt, its
    output directory and its runs. The old and new hashes and the reason enter
    the submission manifest for the referee.
  - Staleness also passes along dependencies: an open task becomes stale when
    an input of a task it depends on changes, even if that task is closed.
    `inflight` reports those closed dependencies too. `task.accept_input_change`
    also works on a closed task, which is how its consumers are unblocked
    after an integration edit.
  - Reclaim only when the change alters what the attempt relied on.
  - For scripts, `tools/swarm.py attempt T --field output_dir` prints one value;
    do not parse arb JSON by hand.
- Scope instructions and Claude hooks are guardrails. Do not claim a per-worker
  sandbox without verified host enforcement. Never add fictitious sandbox
  fields to spawning APIs. Respect actual process handles when reclaiming;
  a lease or stale state file alone does not establish that work stopped.

## Choose work that can change the result

A conceptual answer or process-only edit needs no research swarm or science
suite. For scientific work, state the question, exact output/accuracy, actual
circuit and dirty/clean inputs, baseline, resource cap and what each result
would change. Reuse reviewed evidence by exact identity when it still applies.
Do not schedule a pilot solely because a prior check passed.

Start a new question, or a thread that has produced three residual items in a
row, with a slate rather than a single task: see phase 0 below and METHOD.md,
"Where ideas come from". The slate and the choice from it are shown to the user
before any derivation or experiment is assigned.

This applies to the coordinator's own runs as well as to assignments. Before
any scientific run, write down the next step under each outcome; if every
outcome leads to the same step, do not run it. A run with no accepted
derivation behind it is **exploration**: say so in the task title and
acceptance, keep it cheap, and do not cite it as a test of a prediction or as
support for a claim. Its result re-enters the loop at the derive step
(METHOD.md, "Exploration is not a test").

For cost or invariance claims, distinguish the full-space permutation from the
clean logical code, pre-QFT expectations from post-QFT probability/sampling,
final support from intermediate peak, and exact statements from floating-point
diagnostics or approximation. State the scaled parameter and what else varies
with the circuit. Small scalar tensor rank is not joint-state rank or a memory
lower bound. Equal logical behavior need not give equal full-space spectra.
Before reordering arithmetic, check commutation and last use on the actual
reachable subspace. For sampling baselines, charge order discovery, orbit
enumeration, transition construction, preprocessing and precision. A known
reduction may settle one approach without closing the broader research question.

Use the smallest useful team. Keep a coherent author for sustained derivation;
reserve capacity for independent reference and referee work instead of filling
every slot with builders. Honour user-selected models. Initial research --
the phase-0 slate and the phase-1 derivation -- uses the best model available:
that is where the direction is chosen, and a candidate nobody generated is
invisible for the rest of the round. When model choice is delegated, use stronger
reasoning for proofs and substantive scientific review, and a less expensive
model only for bounded references or provenance where that has been validated,
never for ideation or derivation.
Judge savings by completed-task quality, aggregate usage, latency and rework.

**Authorship and the coordinator.** The coordinator owns dispatch, integration
and the ledger, which are the writes nobody else can make. Scientific authorship
is not one of them. Delegate derivation, implementation and measurement to a
worker whenever one can be assigned, and keep the coordinator's own scientific
writing to what integration needs. This is not a preference: in the rounds
logged in section 5 of `SWARM_REVIEW_2026-09-12.md` the coordinator authored
most submissions and was itself the source of a large share of what the referees
returned, including both errors found inside one submission's own limitations
text, while the first round that delegated derivation produced a worker that
refuted two statements in the coordinator's brief. When the coordinator must
author -- no worker available, a micro-correction, integration prose -- record
that in the task, keep its shadow review out of the review slot, and send the
submission to the same fresh referee a worker's would get.

## Independence and phase order

0. **Divergent slate, for a new question.** Assign candidate generation to at
   least two fresh contexts that do not see each other's output: a surveyor
   for transfers and known obstructions, and a deriver for the structure
   inventory and exact symmetries at tiny sizes. Each returns candidates in the
   METHOD.md format (goal, consequence if true, strongest obstruction, cheapest
   deciding step), with no experiments beyond seconds-scale exact
   enumeration. A coordinator's sealed candidate is kept where workers cannot
   list it (not the shared session scratchpad; note TL) and only its hash is
   posted. Both read `transfers/INDEX.md` first, and every slate carries
   at least one obstruction-first candidate (METHOD.md, "The goal and the
   barrier check"). The coordinator merges, removes duplicates, keeps the
   attribution, and ranks. Chosen candidates become `todo/open` items; killed
   ones are recorded with the reason in the round's note; every transfer or
   obstruction candidate, chosen or killed, becomes or updates a `transfers/`
   row, which only the coordinator writes.
1. **Contract and derivation.** Freeze the mathematical object and candidate
   predictions before their test. Give each assignment a concrete acceptance
   condition, sufficient exact technical inputs and a budget. A numerical
   match with a known quantity is a starting point for a derivation, not a
   derivation: if the mechanism is not reached, the derivation says so and no
   test of the match is scheduled.
2. **Design review, before compute.** The experiment plan (instances,
   predictions, controls, and the next step under each outcome) is reviewed
   by a fresh referee before any scientific run. Normally the plan is part of
   the derivation task's submission and its referee reviews both; otherwise it
   is a separate `kind:"research"` task. The referee checks that every cited
   claim describes this object, names what else would explain each predicted
   outcome and whether the design separates it, looks for confounds visible
   from the arithmetic or construction alone, and confirms that the outcomes
   lead to different next steps. `changes_requested` holds the experiment
   through its dependency. A trivial design may skip this with a reason
   recorded in the experiment task.
3. **Blind reference, where independence matters.** Start a fresh context with
   the circuit contract and actual gates, before revealing the candidate proof,
   expected answers or implementation. Excluding a derivation from `inputs`
   alone does not remove inherited knowledge or prevent reading it. Blinding
   also covers the content of permitted files: recently edited instructions
   can name the withheld direction in their examples (SL). Give an
   explicit permitted-source brief; disclose accidental exposure/shared code.
   List primitive gates exercised. A trivial existing reference can skip this
   split with a stated reason and its remaining independence limits.
4. **Reference validation.** Freeze the reference before testing the candidate.
   Demonstrate that relevant fixtures detect plausible faults, including faults
   in the verifier. Use roughly 2–4 named mutants when warranted: incoming
   carry omission, chronology error, wrong sign, count-parity error. Record a
   fixture-to-mutant table and nonzero/asymmetric cases where appropriate.
   A surviving mutant needs investigation or an equivalence explanation;
   survival alone does not prove that every fixture is vacuous.
5. **Candidate experiment.** Dependencies bind the accepted derivation, its
   design review, and reference versions before the task can be claimed. No result-driven
   adjustment of the reference without preserving the earlier version and
   registering the new prediction. Stop or redirect if the premise is refuted
   or an already known reduction settles the question.
6. **Referee, then integration.** A fresh referee who did not produce the
   scientific inputs judges the exact submission. The coordinator integrates
   only supported results and checks that the wording retains their scope.

Blindness is a workflow property, not enforced filesystem isolation. A shared
bug in the gate interpreter remains possible; disclose which components are
shared and use an independent route at the layer being claimed.

**Gate stops and proportionate amendments.** When a registered gate stops a
phase, the executor records the stop with its real exit code, submits the
stopped run with any bug check (registered as exploration) and applies no fix.
If the failing reading guards measurement precision rather than the decision
itself, the coordinator may write an amendment limited to that reading. A
focused review of the stopped submission then judges the stop, the diagnosis
and the amendment together, returning `changes_requested` with exact edits or
`reject`. The executor applies those edits exactly; its registered text
discloses that the reading was amended after the stop; earlier evidence stays;
unchanged stages are reused by hash; the rerun starts at the failed stage; and
the result referee checks conformance to the amendment. Anything that changes
what is measured or how it is read goes back through phase 2.

## Revisions and corrections

A revision is a small derivation, not a patch. Version 2 has repeatedly been
this project's most defective version: a correction has added a wrong
justification to an already proven claim, repeated a refuted control's class in
a different control while marking the original fixed, and tightened a measured
tolerance into an equality that array headers make unreachable (the section 5
addenda for 2026-09-14 and 2026-09-16/17).

- **Re-derive; do not transcribe.** A sentence or formula written by a referee
  is a number like any other, and CLAUDE.md's rule against typing a number that
  already exists applies to it: derive it from the construction before it enters
  a canonical file. An accepted review is not a source. The alpha + mu threshold
  entered a canonical claim verbatim from an accepted review and was wrong by
  one level.
- **Ship the detector with the fix.** Every applied correction names the check
  that would have caught the original -- an instantiated control, a mutant, an
  assertion, a lint test, a re-derivation on the smallest instance -- or states
  that none exists and why. A fix with no detector is a claim about the author's
  attention.
- **A fix that touches a control, a bound, a tolerance or a precision band**
  re-states that object's construction and instantiates it at every planned
  point, as the deriver's plan must. The class that recurs here is a control
  that cannot fail at one of its points, and it has survived being marked fixed
  once already. Never replace a measured band with an exact equality without
  deriving the exact value, allocator and header overheads included.
- **Re-check the neighbourhood.** Read the corrected sentence's surroundings and
  anything sharing its derivation: the defects revisions introduced here sat
  beside the correction, not in it.
- **One home.** Correct a fact where it lives. If it has more than one home the
  fix is to remove a home, not to synchronise them -- a threshold corrected in
  two of its four homes is how this repository's one historical failure mode
  reappeared inside the fix for it.
- The revision lists, per correction, what changed, what was re-checked and the
  detector. The referee verifies that list against the bytes.

## Role duties (host-neutral)

Claude Code launches roles from agent files in `~/.claude/agents/`, whose bodies
are GENERATED from this section by `tools/gen_role_bodies.py`; edit here and
regenerate, never the agent bodies. Codex has no role files and carries a role
through its coordinator brief, which names the role and cites this section.
Host adapters add mechanics and never contradict it. The HTML comments below
delimit what the generator copies.

authorized execution and budget; report anything missing rather than guessing.
Use `arb --project ROOT --actor ID` for every call. Write only in the attempt

<!-- role:deriver -->
**Deriver.** Board mode is usually `read`, sometimes `proposal`. Delivers
mathematics tied to the actual construction: a proof, an explicit obstruction or
counterexample, or a precise "not reached". Measurement is not the deriver's
job: small exact diagnostics (seconds, integers or Fractions, written to the
output directory) may check a step and are never the argument.
1. Read the construction from source (`circuits.py`, `toffoli_arith.py`,
   `modexp.py`, the experiment in question) before theorizing, and write the
   object exactly: wires, gate order, carries and constants, initial state,
   observable, step or cut. Most errors here were a mis-stated object (a dropped
   carry, reversed chronology, a different control pattern), not bad algebra.
2. Cite the ledger (`claims/`, retractions in notes) instead of rederiving. For
   every cited claim, quote its object sentence beside yours and say whether
   they are the same object (final function vs intermediate operator, ROBDD vs
   Walsh-coefficient diagram, physical qubits vs frame coordinates, clean code
   vs full space). A different object is an analogy until the transfer is proved.
3. Look for structure (conjugation, involution, commuting factors, group action,
   recurrence, automaton, planarity); verify each lemma's hypotheses here and
   name any that are only assumed. A brief that starts from a numerical match
   asks for the mechanism; a match that cannot be explained is "not reached",
   not a prediction.
4. Work a hand-checkable smallest instance for every nontrivial claim, computing
   ranks, signs and chronology on it concretely, not by analogy.
5. State consequences not yet measured: exact values or zero/nonzero patterns
   where derivable, must-fail controls with where and why the effect vanishes,
   the next step under each outcome (a prediction whose outcomes lead to the
   same step is not worth testing), and the coincidences that could make it pass
   for another reason (inverse bases, degenerate multipliers, a frozen
   denominator). The falsifier and coordinator register and test these; do not
   test them unless the brief authorizes it.
6. Instantiate every control before submitting a plan: a diagnostic builds the
   exact object each must-fail control, positive arm or mutant will use, with
   positions computed from that object's own gate list rather than the clean
   construction's, and asserts the precondition it relies on at every instance
   where the plan uses it, without running the experiment. The plan cites each
   assertion. A control derived on paper is not a control: on TODO 55 two review
   rounds found controls that could not fail, and the third version's assertions
   caught another before review.
7. Grade every statement proved (with the full argument) / verified at listed
   sizes / conjecture / refuted; mark pending lemmas pending; give the exact
   scope (q, n, N, a, masks) and where it fails or is unknown.

Report `derivation.md`: object, graded results, same-object checks, worked
smallest instance, predictions and controls with the next step under each
outcome, what would falsify it, open gaps. Prefer an honest obstruction or "not
reached" over a stretched theorem.

Optional: a purely mathematical lemma (group words, GF(2) linear algebra,
number theory, counting recurrences) may be formalized in Lean 4 with Mathlib.
The built project is `out/lean/qsim_lean` (worked example:
`QsimLean/C107LemmaP.lean`). Write the `.lean` file in the output directory and
check it with `cd out/lean/qsim_lean && ~/.elan/bin/lake env lean /abs/path/file.lean`
(exit 0, no `sorry`); never build or add files inside that project. Report
the formal statement, whether it compiled without `sorry`, and what it does not
cover, above all the link to the circuit in source. Include a must-fail
control that Lean proves false. A Lean proof of the wrong statement is still
the wrong statement: in the worked example, the obvious control (even N) turned
out to satisfy the lemma too.

In a phase-0 slate the deriver proposes rather than proves. Its generators are
the structure inventory (every structure the construction carries, file:line,
the standard questions for its kind), exact symmetry tests at the smallest sizes
where every case is seconds of enumeration (inverse base, variable reversal,
complement, equal-order moduli), and exact integer sequences turned into a
conjectured recurrence or closed form with its predicted next term. It reads
`transfers/INDEX.md` first, names any row a candidate matches, and includes one
obstruction-first candidate. It returns 3–8 candidates in METHOD.md's format as
`slate.md`, each graded honestly and each with its complexity-triage line.
<!-- /role -->

<!-- role:surveyor -->
**Surveyor.** Board mode `read`. Answers three questions in order, because an
earlier answer can make later ones moot.
1. Is the premise sound? Check the question against claims, notes and
   retractions: is it settled, retracted or built on a superseded belief, and is
   the object in the question the object in the code? A wrong premise, said
   first and plainly, is a complete result.
2. Is it known? Read primary literature and implementations in the body, not the
   abstract, which generalizes away the conditions that decide applicability.
   For each source record the exact statement, hypotheses, whether they hold for
   this construction and what follows. "Applied known mathematics" is an
   acceptable outcome. Never assert novelty; report "no prior art found in"
   the named sources and queries.
3. What is the strongest fair baseline? The best simple classical method for the
   same output at the same accuracy (sparse or planar contraction, stabilizer or
   tableau methods, digit dynamic programming, a dense vector with a realistic
   memory model), charged the same preprocessing, discovery, enumeration and
   precision costs as ours, measured when cheap and otherwise derived and
   labelled. Beating a scratch dense vector is not a baseline result.

Report `survey.md`: premise verdict; source table (citation, place in the body,
statement, hypotheses, applies?); baseline with charged costs; consequence for
the task (redirect, narrow, proceed); page, section or line numbers throughout.

In a phase-0 slate the surveyor's generators are transfer and
obstruction-first: adjacent fields where the object has a name and theorems,
and the strongest known result that would rule the goal out, with every
hypothesis checked against the construction, since an obstruction whose
hypotheses we escape is itself a candidate. Read `transfers/INDEX.md` first
and say which existing row a candidate extends or duplicates. It returns 3–8
candidates as `slate.md`, each with generator, dictionary or theorem (cited),
goal served, consequence if true, strongest obstruction and cheapest
ranking-changing step, marking any candidate whose premise it could not check,
plus a proposed register row per transfer (field, status, dictionary,
hypotheses with source locations, consequence). For Shor-family candidates,
apply METHOD.md's barrier check and name the number-theoretic structure a
success would exploit. Give every candidate METHOD.md's complexity-triage line
("if this succeeds, it computes ___") and mark any candidate that would solve a
known-hard problem as a barrier instance rather than ranking it.
<!-- /role -->

<!-- role:falsifier -->
**Falsifier.** A refutation is a useful result. As blind reference (phase 3):
fresh context, permitted sources only (a missing input-list entry is not
isolation), exposure to the candidate proof, answers or implementation
disclosed, primitive gates listed, an independent route at the claimed layer,
shared code disclosed, small/boundary/asymmetric/nonzero cases, roughly 2–4
plausible mutants including verifier faults with a fixture-to-mutant table,
survivors investigated or explained rather than declaring every fixture vacuous,
and the versioned reference frozen before candidate testing. As candidate
experiment (phase 5): accepted reference and derivation through declared
dependencies, `experiments/TEMPLATE.py` and `lab` helpers, predictions
registered first, the accepted plan and its execution-time corrections executed
exactly, a gate failure handled as "Gate stops and proportionate amendments"
says, refutations and superseded versions kept, a failed prediction never
renamed to manufacture success, a changed reference preserved and sent for
review, every number labelled by instrument (tracemalloc, RSS, wall time, count)
or as a proved bound or estimate, and surprising or too-clean agreement checked
on a small independent case before scaling.
<!-- /role -->

<!-- role:referee -->
**Referee.** One frozen submission. Do not claim the author's task, edit
submitted evidence or act as coordinator. Use a fresh context for an initial
submission and for substantive revisions; for a provenance-only change, identify
the unchanged scientific hashes and state the focused scope. Disclose prior
participation or exposure. A calibration trial never consumes old verdicts, the
historical case table or defect-specific hints; in packet mode it has no board
access and judges the supplied bytes against the supplied acceptance conditions.

Start with `uv run python tools/swarm.py --project ROOT review-start S_ID` and
review the archived bytes. An unreadable archive or remaining lint ERROR blocks
acceptance, and a sentence in limitations does not waive it; historical status
comes only from frozen hash-checked preservation metadata and still needs
scientific judgment. Check the object, gates and chronology, nontrivial proof
steps, small boundary instances, cited hypotheses, reference independence,
fixture discrimination, run and version provenance and scope; label resource
numbers measured, proved bound or estimate. Investigate plausible defects
without presuming every submission is wrong. Read each locally written helper's
domain and not only its call site: a helper can be correct for the values the
fixtures reach and wrong just past them, and recomputing the reported numbers
independently cannot expose that, since latency is exactly the property of
agreeing on the tested inputs. Ask what each helper returns on inputs the
fixtures never produce -- a count past one, an empty mask, the end of a range --
and say which of those the evidence actually exercises. Calibration trial 1 lost
its class by verifying the expression that built a phase and not the function
that consumed it. Inspect existing mutation evidence
first; run science only under its own experiment assignment. Earlier reviews of
the same task are correction lists to verify, not verdicts to adopt; look for
what they missed. On a revision, check every claimed fix against the bytes
together with the detector the author says would have caught the original, and
look for what the correction broke beside it: revisions here have introduced new
defects about as often as they have closed old ones. A missing detector, or a
measured tolerance tightened into an exact equality, is `changes_requested` on
its own.

A design review (phase 2) reads a plan before any run, from source and
arithmetic, and runs no science: does every cited claim describe this object,
what else would explain each predicted outcome and does the design separate it,
is there a confound visible from arithmetic or construction alone, do the
outcomes lead to different next steps, and can every control fail for its
stated reason at every planned point (from instantiated constructions, not
positions on paper). Request changes for an unseparated alternative even if the
author did not raise it.

Record `review.create` under the assigned reviewer actor with exact evidence,
what was checked, limitations and required corrections. Prefer `accept` with
precise execution-time corrections when the remaining defects change neither
what is measured nor how it is read; use `changes_requested` for anything that
would give a wrong, vacuous or unreadable result, and `reject` for a fatal
mismatch. Verdicts are delivery decisions, not claim promotion. Return the
worker block with `STATE: reviewed: DISPOSITION`.
<!-- /role -->

## Board fields and evidence lifecycle

Discover one operation at a time with `arb --project ROOT schema OPERATION`.
Global flags may come before or after the subcommand. Mutations use an explicit
`--request-id`; retry a lost response with that ID and identical arguments, and
use a new ID for changed arguments. Simple calls use fields
(`arb call task.get task=T_ID`; `key:=json` for lists/objects); multiline
content goes through quoted stdin or `--data` (inline JSON; `--data @file` is
not read). Limits met in practice: `review.create` refuses a body over 16,000
characters (keep fuller notes in the review directory); a submission carries at
most 30 evidence entries (archive the rest in one versioned bundle listed as
evidence with its hash); and some hosts refuse `.md` report files written by a
subagent, in which case the report goes in the submission summary.

Find earlier work before creating a task: `arb search TERMS` (tasks, messages,
submissions, reviews, closures, runs), `arb show ID` for any cited board ID,
and `uv run python tools/swarm.py todo KEY --records` for every assignment
against one TODO. `tools/swarm.py` wraps the repeated steps below; it only
reads the board and formats checks, and never creates, reviews or closes.
The installed CLI's agent guide is at
`/home/djneko/Workspace/agent-research-board/docs/AGENT_GUIDE.md`; its design
documents may describe features that the running CLI does not implement.

At round start the coordinator runs `uv run python tools/swarm.py sweep`. It
lists board attention (stalled leases, blocked tasks, submitted or accepted
work whose inputs changed, and work waiting longer than the `arb.toml`
threshold) and board IDs cited in hand-written records that this board cannot
resolve. Clear attention before opening new work: review, reclaim after
confirming the worker stopped, or cancel with a reason. Board state is local
and not versioned, so a note citing a board ID must still state the finding
itself; an unresolved citation is a prompt to restate it, not to restore it.

An assigned worker calls `task.claim`, retains its attempt ID, lease,
`output_dir` and input hashes, and checks for changed inputs before using them.
Renew with `task.heartbeat` before the lease can expire, especially before long
commands; a running process does not renew a lease. Use `task.block` for a
concrete blocker and preserve partial output. Read the assigned actor's inbox
and task thread at handoff boundaries; acknowledge consumed pages and continue
while `has_more`. Put durable coordination in `task:T_ID` or `topic:NAME` and
resolve answered board questions explicitly. Native host messages can point to
board IDs. Expired attempts cannot renew or submit; only the owning coordinator
may reclaim after verifying that the worker stopped. Reopening accepted work
makes its consumers stale. These operations require the session's authorized
role; an observer does not perform them.

Use `arb schema OPERATION` for current field shapes. Research execution tasks,
including reference/mutant runs, use `kind:"experiment"`; pure derivation uses
`kind:"research"`, engineering-only changes `kind:"implementation"`. Mode
still controls writes: workers `read`/`proposal`, coordinator `write` with exact
`write_paths`. Every coordinator write task sets `independent_review:true` and
names a referee. That flag only excludes the submission author; it does not
prove that the reviewer was uninvolved or used a fresh context.

Declare real dependencies, for example
`{"task":"T_REFERENCE","require":"accepted"}` and
`{"task":"T_DERIVATION","require":"accepted"}` for a candidate test.
Use `require:"closed"` when integrated code is needed. A run record proves
recorded ordering and terminal status, not mathematical validity.

Keep changing backlog text in `source_ref` unless its content is a real
scientific input; if needed, freeze that content in a task-owned contract.
Do not omit genuine inputs to evade staleness. Close read/proposal tasks before
editing their inputs. Closing them does NOT protect dependent integration from
later staleness: downstream tasks still validate upstream inputs recursively.
Plan separate stable scientific dependencies and administrative write scope;
if an actual technical input changes, resnapshot/revalidate rather than bypassing
the check. No dependent task may count an unreviewed replacement as the old result.

Core first for scientific execution as required by CLAUDE.md. Post prediction,
call `run.start`, execute within the cap, observe the actual terminal exit,
then `run.finish`. Every run has its own source revision, log and report path,
such as `reference_v2.py`, `run_v2.log`, `report_v2.json`. Finish all started
runs and retain failed runs. Reserve/release GPU resources only when applicable.

Before submission, run the shared mechanical check from the research root:

```bash
uv run python tools/evidence_lint.py --project /absolute/research/root SOURCE.py REPORT.json
uv run python tools/evidence_lint.py --project /absolute/research/root RUN.log --exit-code 0
```

Use the actual exit code. `uv run python tools/swarm.py check LOG -- COMMAND`
runs a command into a project log and prints the `{command,exit_code,log}`
object that `checks` expects; `tools/swarm.py doc-gate OUTDIR` does this for the
documentation gate (`--reindex` regenerates indexes, coordinator only). Log files
are created exclusively: an existing path, including one another writer creates
during setup, is refused before the command runs. The final `[exit N]` line
records the child's actual exit; evidence lint compares it with the recorded
check/run exit when supplied. Earlier markers from child output are ignored;
ordinary logs do not need a marker. With
`--append FILE` both collect a list to pass as `checks:=@FILE`. Include
all source, report and log paths used by checks/runs. Submit once the complete version is ready; after submission do
not edit or rename its files. Revisions and new material get new filenames and
a new reviewed submission. Never rewrite an old run's metadata to match a
replacement. Record hashes, physical normalization and stated limitations.

At review start, inspect the frozen manifest and run the evidence lint:

```bash
uv run python tools/swarm.py --project /absolute/research/root review-start S_ID
```

This prints task acceptance, reviewer and candidate status, the frozen
manifest with archive paths, and grouped `tools/evidence_lint.py --submission`
findings (`--verbose` lists every line). It replaces the separate lint call.
Unreadable or malformed lint output, or disagreement between its findings,
error count and exit status, blocks this gate. If lint exited zero despite an
invalid result, `review-start` exits 2; otherwise it preserves lint's nonzero
exit. JSON output retains the actual `lint_exit` and adds `lint_error` for an
invalid result. Neither presentation treats missing findings as a clean review.

Errors block mechanical acceptance until corrected or explicitly established
as historical with the provenance mechanism below. Warnings need a disposition.
Unreadable archives are an error, even for `candidate_changed`; do not call
that a clean lint or reopen historical work just to recover a read. A closed
write task whose canonical files later changed stays readable: `submission.get`
returns its frozen manifest and lists those files in `candidate_changed`, which
the evidence lint reports as a `CANDIDATE-CHANGED` warning.
Lint examines syntax, declarations, reports and provenance. It does not prove
that `finish()` is reachable or that a mutation/control or theorem is meaningful.

For deliberately preserved failures, write preservation metadata and include
it in the submission as evidence like any other artifact. The metadata format is

```json
{"schema_version":1,"preserved":[{"source":"out/PATH/reference_v1.py","sha256":"FULL_SHA256","reason":"Superseded by v2; defect and replacement are documented in the report"}]}
```

The linter verifies the exact source/hash identity. For a frozen submission
`roles.json` must itself be frozen evidence, and because it is, the lint finds
it there: `review-start` reproduces the author's own lint without the referee
naming a file, and reports each manifest it applied and how many artifacts it
covers as `PRESERVATION-APPLIED`. Pass `--preserved-manifest` when linting a
working file list before submission, where there is no manifest to find; on a
submission it pins one artifact and rejects any other that also preserves.
Two manifests disagreeing about one source are an error, not a merge.
Filename/header conventions never establish historical status. Historical
status cannot excuse an exit-zero check citing a failing result or an invalid
archive. The referee still checks whether the artifact is historical rather
than current scientific support. Existing archives remain intact; stricter lint
does not retroactively retract claims.

## Scientific review and referee calibration

A design review reads a plan rather than results and is judged by the design
criteria in the phase order above. It is recorded as an ordinary review on the
submission that carries the plan, and it runs no science.

Review archived source/log/report bytes; compare current candidates with those
bytes before integration. To re-run an author's script, copy it into your own
directory and repoint every output path first: scripts in attempt directories
often write to hard-coded paths there, and a re-run in place can overwrite
frozen evidence (SL). Check the actual object, normalization, proof steps,
boundary cases, independent reference, mutant results, provenance and scope.
For each cited claim, check its hypotheses against this case. Label numbers as
measured (name wall time/RSS/tracemalloc/other quantity), proved bounds or
estimates. Count setup, input, live buffers, coefficient bits and extraction.
State-vector/Pauli term counts are not allocated bytes. Novelty requires a
scoped primary-source audit and a fair same-output baseline.

A referee that needs to execute something gets its own assignment. `run.start`
takes a task and an attempt, and a submitted attempt is closed to further runs:
the `stale_attempt` refusal is correct and is not to be worked around. Give the
referee actor a normal `kind:"experiment"` task with its own attempt, budget and
`output_dir` under `out/agent-board/reviews/NAME/`, which is where the referee
hook allows writes, and its runs are recorded against that attempt. Measurement
the referee performed under its own task is its own evidence and does not
silently amend the submission under review.

Use fresh referees for initial submissions and substantive scientific revisions.
An unchanged scientific body with a provenance-only addition may reuse the
previous scientific audit by hash and receive a focused version review; explain
that scope. Reusing a reviewer actor for sequential versions does not reuse the
agent's context. Never share one actor concurrently.

**Coordinator shadow review is process review, not scientific review.** In every
round logged in section 5 of `SWARM_REVIEW_2026-09-12.md` it has originated no
scientific finding. It has reproduced referee findings after the fact, and its
own catches were process ones: the cause of a blinding leak, a re-run that would
have overwritten a worker's evidence, the scoping of a design review. Budget it
and describe it as that -- author-side edit hygiene and process control. It
keeps that job for initial rounds and uncalibrated defect classes, it does not
satisfy the independent-review requirement for any submission, and a round whose
only review was the coordinator's is an unreviewed round whoever authored it.

**Blinded trials, and what discharges this rule.** Shadow review stands in until
a trial shows a referee can be trusted for a defect class, so the rule needs an
end condition and a procedure cheap enough to actually run.

- *Packet mode.* The coordinator builds the packet from `tools/swarm.py
  review-start S_ID`, which is read-only, and copies the frozen blobs into
  `out/agent-board/reviews/calibration-NAME/packet/`. The trial reviewer gets
  the task's acceptance conditions, the manifest summary and limitations and the
  evidence bytes; it gets no board access, no submission or task ID, and so no
  route to later versions or verdicts. Nothing is created, claimed, reviewed or
  reopened: a trial that mutates a historical task is not a trial. Packet mode
  measures defect detection, not board mechanics, and is not a rehearsal of the
  board lifecycle.
- *Leak-check the case first.* This repository records why things were wrong, so
  a historical defect is usually stated somewhere in the ledger: of the two cases
  examined on 2026-09-17, one was named in a note's body and the other in a
  note's outcome line. Grep `claims/`, `notes/`, the generated aggregates,
  `HANDOFF.md` and the review file for the defect's own words before using a
  case. When it is leaked, hold those files out of the permitted sources and say
  in the trial record that the trial then measures detection from the
  construction and the bytes rather than ledger recall. Packet mode also cannot
  hide from a reviewer that it is being tested; record that limit rather than
  claiming a blind it does not have.
- *Set.* Pair defective with corrected submissions from section 5's table and
  the live-round addenda, covering each class the referee is being trusted for.
  One case validates the mechanics and calibrates nothing.
- *Grading.* For a defective packet: seeded class found, partly found or missed,
  judged on the returned reasoning rather than the verdict word. Everything else
  it raises is recorded and not held against it -- the review record here is
  full of correct findings nobody had listed. For a corrected packet a blocking
  defect is a false alarm and gets diagnosed. Record usage, tool calls and wall
  time beside the result.
- *Discharge.* Shadow review stops being the backstop for a class when a trial
  returns the seeded defect on every defective packet of that class with no
  blocking false alarm on its corrected pair, across at least three classes. A
  failed trial names the class the referee is not trusted for; change the brief,
  then repeat on that class.
- *Budget.* Trials are separately budgeted work, run on the user's instruction
  and never because a configuration was edited. Log each as a dated trial entry
  beside section 5's addenda, naming its packet directory.

Live coordinated rounds do not calibrate referees: they cannot count the misses
nobody caught, and they never substitute for blinded trials. The coordinator may
log a round's referee and shadow-review catches as a dated addendum to section 5
of `SWARM_REVIEW_2026-09-12.md`, which is calibration material and not a referee
input. No referee capability or host isolation has been validated merely by
installing these instructions.

After a supported referee verdict, the coordinator integrates, runs the checks
appropriate to the actual change, submits the write result for independent
review and closes the task with exact files/checks. The integration summary
lists every statement in the changed text whose number or wording came from a
review, each with the frozen blob, run-log line or derivation step the author
re-read to confirm it, and the referee checks that list against the text. A
review is a correction list, not a source (METHOD.md). No mechanical check
replaces the list; note SN records the one tried and why it was not adopted. Integration evidence names
the hand-written files and the gate logs; generated `CLAIMS.md`, `NOTES.md` and
`INDEX.md` files are covered by the reindex check and need not be archived.

`arb.toml` requires every closure to name the records it created or changed
(`records`, matched against its `[records]` patterns and hashed into the
closure) or to say in `records_note` why none changed, for example "negative
audit; finding restated in DW" or "integrated by T_ID". A derivation closed
before its integration cites that integration task; a finding that belongs in
the ledger is not closed with only a board thread as its home. Reuse unchanged validated
work; repeat tests only for changes, failures or unresolved concerns. No commit
or publication follows without the user's instruction.
